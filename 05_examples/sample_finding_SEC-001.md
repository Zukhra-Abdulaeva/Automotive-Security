# SEC-001

## Title

Unauthorized access to protected diagnostic operation

## Severity

High

## Asset

Protected Diagnostic Operation

## Affected Component

`security_lab.ecu_simulator.ECUSimulator.handle_request()`

The affected behavior is limited to the controlled `VULNERABLE` simulator mode used to reproduce the pre-fix security finding.

## Security Requirement

Protected diagnostic operations shall require authorization.

## Description

The controlled vulnerable ECU simulation grants access to the protected diagnostic operation when authorization is disabled.

The required behavior is `ACCESS_DENIED`. The vulnerable implementation instead returns `ACCESS_GRANTED`.

The behavior is intentionally implemented in the simulator to provide a reproducible pre-fix condition for the security regression workflow. It does not represent a finding against a real vehicle, ECU, OEM system, or production implementation.

## Threat Model

- **Asset:** Protected Diagnostic Operation
- **Threat Actor:** Unauthorized diagnostic client
- **Attack Surface:** Simulated diagnostic request interface
- **Security Property:** Authorization must be enforced before execution of the protected operation.
- **Potential Impact:** Unauthorized execution of the protected operation within the controlled ECU simulation.
- **Assumption:** The simulated ECU is responsible for enforcing authorization before granting access.

The assessment is restricted to the controlled simulation. No claim is made about access to real vehicle functions or production systems.

## Preconditions

1. ECU simulator is running in `VULNERABLE` mode.
2. Authorization is disabled.
3. ECU is in the `READY` state.
4. The requested operation is `PROTECTED_OPERATION`.

## Reproduction Steps

1. Start the ECU simulator in `VULNERABLE` mode.
2. Set the authorization state to `false`.
3. Send a request for `PROTECTED_OPERATION`.
4. Record the returned response status.
5. Compare the result with the security requirement.

```text
Authorization: false
ECU mode: VULNERABLE
ECU state: READY
Input operation: PROTECTED_OPERATION
Expected: ACCESS_DENIED
Actual: ACCESS_GRANTED
Result: FAIL
````

## Expected Behavior

An unauthorized request for the protected operation must return:

```text
ACCESS_DENIED
```

## Actual Behavior

The controlled vulnerable implementation returns:

```text
ACCESS_GRANTED
```

even though authorization is disabled.

## Security Impact

The demonstrated impact is limited to the controlled ECU simulation.

An unauthorized diagnostic requester can cause the simulated ECU to return `ACCESS_GRANTED` for the protected operation while authorization is disabled.

The simulation does not model real vehicle control, real ECU access, production diagnostic networks, customer data, production credentials, or physical safety functions. No impact beyond the demonstrated simulated authorization failure is claimed.

## Exploitability

The behavior is deterministic and can be reproduced with low execution complexity once the controlled vulnerable simulation is available.

* **Preconditions:** Vulnerable simulator mode, authorization disabled, `READY` state, protected operation.
* **Required access:** Access to the simulated diagnostic request interface.
* **Required knowledge:** Knowledge of the supported protected operation.
* **Complexity:** Low within the controlled simulation.
* **Repeatability:** Deterministic and reproducible.

These characteristics apply only to the controlled simulation and do not represent a real-world attacker assessment.

## Root Cause

The root cause is the ordering of the authorization decision in `ECUSimulator.handle_request()`.

After request, operation, parameter, and state validation, the deliberate vulnerable branch returns `ACCESS_GRANTED` when the simulator is running in `VULNERABLE` mode.

Authorization is therefore not evaluated before access is granted.

```text
Validated request
    |
    v
State check
    |
    v
VULNERABLE mode?
    |
    +-- yes --> ACCESS_GRANTED
    |
    +-- no --> authorization check
```

This branch intentionally reproduces the security defect defined by TC-001.

## Recommendation

Enforce authorization before granting access to the protected diagnostic operation.

The authorization check must not be bypassed when evaluating a protected operation.

The resulting behavior should remain deterministic so that unauthorized rejection and authorized access can be verified independently.

## Fix

The secure simulator path evaluates the authorization state before granting access to the protected operation.

The controlled `VULNERABLE` branch remains available only to reproduce the pre-fix behavior required by the regression workflow.

```text
Protected operation request
    |
    v
Authorization check
    |
    +-- unauthorized --> ACCESS_DENIED
    |
    +-- authorized ----> ACCESS_GRANTED
```

No additional production functionality is introduced by this fix.

## Retest

The security requirement is verified for both authorization states.

Unauthorized request:

```text
Authorization: false
Operation: PROTECTED_OPERATION
Expected: ACCESS_DENIED
Actual: ACCESS_DENIED
Result: PASS
```

Authorized request:

```text
Authorization: true
Operation: PROTECTED_OPERATION
Expected: ACCESS_GRANTED
Actual: ACCESS_GRANTED
Result: PASS
```

The project test execution provided by the user reports 38 passing tests:

## Regression Test

TC-001 provides the regression basis for this finding.

The regression workflow covers the following security properties:

* Unauthorized access to the protected operation is rejected with `ACCESS_DENIED`.
* Authorized access to the protected operation remains possible with `ACCESS_GRANTED`.
* The vulnerable pre-fix behavior remains reproducible for comparison.
* Evidence can be generated from the test result.

The centralized regression suite and CI/CD integration are outside the scope of Phase 8.

Fixed in the controlled simulation.

The secure authorization behavior and regression implementation are present according to the supplied project contents. The project test execution provided by the user reports 38 passing tests.

Independent execution and filesystem verification are not available in the current environment.
