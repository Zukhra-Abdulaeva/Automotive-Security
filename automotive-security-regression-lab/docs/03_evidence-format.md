# Evidence Format

## Purpose

The Evidence Framework provides a deterministic representation of security test
execution results.

Phase 4 introduces structured evidence for the existing Phase 3 security test
execution architecture.

The evidence is generated exclusively from the simulated test environment.

No real ECU data, production credentials, vehicle data, network traffic, or
customer data is included.

## Evidence Model

Each evidence record represents one executed security test case.

The minimum evidence fields are:

- `execution_id`
- `test_id`
- `description`
- `request`
- `expected_status`
- `actual_status`
- `passed`
- `operation`

## Execution ID

Each evidence record contains an `execution_id`.

The execution ID uniquely identifies one test execution within the evidence
set.

The ID is generated by the Evidence Framework and is independent of the ECU
security behavior.

## Status Representation

Expected and actual response statuses are stored using their string values:

```text
ACCESS_GRANTED
ACCESS_DENIED
INVALID_REQUEST
````

The `passed` field records whether expected and actual status values matched.

## Example

```json
{
  "execution_id": "EXEC-000001",
  "test_id": "TC-ARCH-001",
  "description": "Unauthorized protected operation",
  "request": {
    "operation": "PROTECTED_OPERATION"
  },
  "expected_status": "ACCESS_DENIED",
  "actual_status": "ACCESS_DENIED",
  "passed": true,
  "operation": "PROTECTED_OPERATION"
}
```

## Determinism

Evidence must preserve the deterministic result of the corresponding test
execution.

For the same test case, request, target configuration, and execution result,
the evidence content is reproducible apart from the unique execution ID.

## Scope

Implemented in Phase 4:

* structured evidence model
* execution ID
* conversion of test results into evidence
* deterministic evidence representation

Not implemented in Phase 4:

* security findings
* root-cause analysis
* retest workflow
* complete regression orchestration
* CI/CD
* real ECU communication

## Architectural Boundary

The Evidence Framework consumes `TestResult` data.

It does not access ECU internals and does not implement ECU security policy.

```text
SecurityTestRunner
        |
        v
    TestResult
        |
        v
 Evidence Framework
        |
        v
    Evidence
```
